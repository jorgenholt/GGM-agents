Workflow session with Lukas · 23 October · 2 h 46 min

What we learned

Projections are a storyline, not data

Reference production and consumption are anchored to an outlook (IEA WEO) but adjusted node by node. There is no right or wrong version. About a week of Franziska's time.

Elasticities, sector shares, seasonality are judgment too

No data set for them exists anywhere. They are carried over from earlier work or rebuilt for each study.

The general workbook is the most agent-friendly

Mostly factual data (ENTSOG, EIA, Global Energy Monitor, shipping distances), adjusted by scenario assumptions. Lukas already uses AI for the mapping.

Calibration is by hand, with no script

Several days full time. Trial and error with a run between each step. Two scenarios at once: adjust one while the other solves.

Market power is "gut feeling plus some calibration"

Set per scenario. Also used to stand in for long-term contracts and to correct implausible trade.

A new study is a copied folder

Copy an earlier data folder and run script, then edit them. No tooling, and the node structure changes between studies.

What the session changed in our work

Corrected

  • Our four-layer view of the inputs was wrong. Projections are not "read off an outlook". Only the general workbook is mostly collected data.
  • Chapter 3 overstated how much input is collected. It now says judgment sits in two places: the scenario storyline (Franziska) and the calibration (Lukas).
  • Calibration practice is now confirmed, not inferred from the documentation.

Strengthened

  • The thesis gap is stronger: the judgment is not only in calibration, but also in projections that have no ground truth by design.
  • His eight-step workflow with review gates matches the principle from chapter 2: the LLM proposes, code computes, a person decides.
  • His "source plus confidence for every value" is a concrete spec for the agent descriptions in chapter 5.

Research question (provisional)

Where in the workflow around the Global Gas Model could LLM-based agents take over or support expert work, where would ordinary code serve better, and where should the work stay with a person?

Key points

  • Four sub-questions, one for each of chapters 3, 4 and 5, plus one on calibration for chapters 5–6.
  • Scope: we argue from documentation, code, data and literature. We build and evaluate nothing. That is the master's thesis.
  • Contribution: a step-by-step map of the workflow, ending in a description of each proposed agent, and a case the literature has not covered: parameters that carry economic judgment.

Key findings

  • Setting up and running models works inside a harness. MOOSEnger: inputs that run went from 5% for the model alone to 89.5% with validation and feedback. But a run that works is not necessarily a correct one.
  • Calibration agents fall short of experts. HydroAgent: one of nine LLMs matched the expert, at one of four gauges. Fewer runs, but slower and harder to reproduce.
  • How the work is divided matters most. Zhu et al.: failure rate down from 72% to 16% once the LLM only reasons, code does the data work and a person decides at three points.
  • The gap: calibration where parameters carry economic judgment, and preparing data for energy-market models. Golden et al. (2026) come closest, but they only use models with the calibration they already have.

Key findings

  • The model is large. 239 nodes, 125 countries, 2020–2060. One run on a laptop: 5.5 million variables, 24 minutes.
  • Only about 15,200 values in a scenario are collected in the ordinary sense (capacities, distances). The other roughly 18,000 are storyline, earlier studies, settings or calibration.
  • The volume is in the infrastructure data; the judgment is in two places: the scenario storyline and the calibration.
  • Calibration is hard for three reasons. The parameters cannot be looked up, a deviation has several possible causes, and the result must still hold in other scenarios. Between 1,700 and 2,050 calibrated values change from one climate scenario to the next.
  • Six-step workflow: set up the scenario → get source data → prepare data → calibrate → run → read results.

Key findings

  • A workflow, not an agent, where the steps are known. Only steps whose next action depends on what was just found need an agent.
  • The weaknesses matter most, because a wrong GGM input still solves: plausible but wrong values, unreliable arithmetic, agreeing too easily, and explanations that win more trust than they deserve.
  • Tokens are not the cost that decides. About 30 cents per large call, against days of analyst time. What decides is the cost of checking and the risk of an unseen error.
  • Four questions sort each part of a step: is there one answer a rule computes (code)? Is the input unstructured (LLM)? Can the result be checked cheaply (automate)? Would an error be costly and hard to see (a person decides)?
